## 0. 一句话结论

**代码的「书写质量」很高，但「工程约束」几乎为零。**

具体说：没有 TODO 残留、没有 `any`、没有空 catch、没有遗留 `console.log` ——
这些是很多项目最容易烂掉的地方，这里都很干净。

但另一方面：**没有 CI、没有提交门禁、没有错误边界、没有覆盖率**。
质量完全依赖写代码那一刻的自觉，没有任何机制在事后兜住。
一旦连续几次「赶一下」，退化的速度会非常快。

本次审计还**实测出两个真实缺陷**（见 §3），都不是风格问题，是会真正伤害用户的 bug。

## 3. 实测出的真实缺陷

> 这两条是本次审计最重要的产出。它们都不是「写得不好看」，
> 而是会真实伤害用户的 bug —— 而且**类型系统本可以抓到它们**（见 §4）。

### 3.1 🔴 `src/utils/time.ts`：日期解析零校验

六个函数都采用同一模式 —— `split('-')` 之后直接 `Number()`，没有任何校验：

```ts
// 审计前的写法
export function formatChineseDate(localDate: string): string {
  const [y, m, d] = localDate.split('-')
  return `${Number(y)}年${Number(m)}月${Number(d)}日`   // ← 没有校验
}
```

实测输出（`node` 直接复现，可自行验证）：

| 输入 | `formatChineseDate` | `formatMonthDay` | `dayOfWeek` | `monthOf` |
|---|---|---|---|---|
| `""` | `0年NaN月NaN日` | `NaN月NaN日` | `NaN` | `{"year":0}` |
| `"2026-09"` | `2026年9月NaN日` | `9月NaN日` | `NaN` | `{"year":2026,"month":9}` |
| `"bad"` | `NaN年NaN月NaN日` | `NaN月NaN日` | `NaN` | `{"year":null}` |
| `"2026-13-45"` | `2026年13月45日` | `13月45日` | **`0`** | `{"year":2026,"month":13}` |

**最后一行最危险**：`2026-13-45` 不报错，而是被 JS 的 `Date` **静默溢出**成
2027-02-14 —— 不报错，但日期是错的。这比直接失败难排查得多。

**风险入口**：`created_local_date` / `completed_local_date` 会从云端流进来。
一条远端脏数据就足以让界面显示 `NaN月NaN日`。

### 3.2 🔴 `src/utils/time.ts`：`catch` 兜底是**假兜底**，自己也会抛

`localDateOf` / `formatHm` 的写法看起来有兜底，实际上兜底函数**也调用了 `Intl`**：

```ts
// 审计前的写法
export function localDateOf(input, tz) {
  const date = input instanceof Date ? input : new Date(input)
  try {
    return new Intl.DateTimeFormat('en-CA', { timeZone: zone, ... }).format(date)
  } catch {
    return formatDatePartsFallback(date, 'UTC')   // ← 这个函数里也是 Intl.format()
  }
}
```

当 `date` 是 `Invalid Date` 时，`Intl.format()` 抛 `RangeError: Invalid time value`；
进入 `catch` 后，兜底函数**抛出完全相同的 `RangeError`**。

实测：

```
localDateOf('bad')       → ❌ 抛出未捕获 RangeError: Invalid time value
localDateOf(undefined)   → ❌ 抛出未捕获 RangeError: Invalid time value
localDateOf(NaN)         → ❌ 抛出未捕获 RangeError: Invalid time value
```

**后果**：云端一条 `created_at_utc` 格式损坏的记录 → 渲染期抛错 →
React 卸载整棵树 → **白屏**。而按本项目的优先级，「数据不丢」排第一位 ——
白屏会被用户直接理解成「我的记录全没了」。

### 3.3 🟡 `sort()` 修改原数组（11 处）

`Array.prototype.sort()` 是**原地修改**。本次 11 处调用全部作用在新建数组上
（`[...a, ...b]` / `.filter()` / `.slice()` / Dexie `.toArray()`），所以**当前没有 bug**。

但这属于「偶然安全」：只要未来有人顺手去掉那个 `.slice()` 或 `.filter()`，
就会变成静默的共享状态污染。已统一改为 `toSorted()`，把「不修改原数组」变成显式的。

## 4. 类型系统严格度

`tsconfig.app.json` 原本只开了 `strict`。实测开启以下开关的代价：

| 开关 | 开启后的错误数 | 生产代码 | 测试代码 | 决定 |
|---|---|---|---|---|
| `noUncheckedIndexedAccess` | 30 | 5 | 25 | ✅ **已启用** |
| `exactOptionalPropertyTypes` | 5 | 5 | 0 | ✅ **已启用** |
| `noImplicitOverride` | 0 | 0 | 0 | ✅ **已启用**（免费） |
| `noPropertyAccessFromIndexSignature` | **45** | — | — | ❌ 评估后不启用 |

**为什么 `noUncheckedIndexedAccess` 值得付这个成本**：它正是能抓到 §3.1 那类
「`split()` 之后直接取下标」缺陷的开关。实测修复成本只有 11 处生产代码，
而收益是类型系统从今往后帮你守着这一整类问题 —— 性价比极高。

**为什么不启用 `noPropertyAccessFromIndexSignature`**：45 处报错里绝大多数是
`import.meta.env.VITE_X` 的点号访问，改法是把 `.` 换成 `['...']`，
纯粹是写法风格，改动面却很大。收益与成本不成比例，故记录在此、暂不启用。

## 7. 已知缺口（本次刻意未处理）

诚实记录，避免「报告很漂亮、问题还在」：

| 缺口 | 为什么没处理 |
|---|---|
| **无覆盖率统计** | 本项目组件层刻意不做单测（由 E2E 覆盖），全局覆盖率数字会被 UI 拉低到失去意义。**取而代之的是「高风险目录必须有测试」的清单式约定**（见标准文档 §4），这比一个阈值更贴合实际。需要时再引入 `@vitest/coverage-v8`。 |
| **15 个死导出** | 属产品判断，见 §5.2 |
| **`maxIso()` 对非法输入退化为返回 `a`** | 风险极低（调用面是完整 ISO 时间戳），且当前无调用方。已加注释说明，未改契约 |
| **`toDate()` 沿用 JS `Date` 语义** | `new Date('2026-09-31')` 会被 JS **静默滚到 10-01**。这是 JS 自身行为，`parseLocalDate()` 已严格拒绝此类输入；但 `toDate()` 走的是时刻（instant）路径，调用面全是完整 ISO 时间戳，溢出路径实际不可达。**这是一个有意的边界，不是遗漏** —— 已在此记录，避免后人误以为没发现 |
| **`recordRepository.ts` / `ConflictService.ts` 偏大（约 365 行）** | 职责单一，暂不需要拆 |
| **无 CODEOWNERS** | 单人仓库，加了只会拦住自己 |
