# 一刻 —— 代码审查标准与流程

> **适用范围**：本仓库的全部改动。
> **配套文档**：[基线审计报告](./代码审查-基线审计报告.md)（本标准的每一条都来自实测缺口，不是通用模板）、
> [UI 设计规范 V2](./UI-设计规范-V2.md)
>
> 最后更新：2026-09-30

## 0. 这套机制要解决什么

审计（见基线审计报告）发现本项目的问题是**不是「写得差」，而是「没有约束」**：

- 代码本身很干净：0 个 TODO、0 个 `any`、0 个空 catch、0 个遗留 `console.log`
- 但工程约束为零：没有 CI、没有提交门禁、没有错误边界

后果是：**质量完全依赖「写代码那一刻的状态」**。状态好就干净，赶进度就退化，
而且没有任何机制在事后兜住。

所以这套机制的目标不是「增加流程」，而是**把已经很好的书写习惯固化成机器能守的约束**，
让人只需要专注于机器判断不了的部分。

## 1. 判据：本项目的优先级

代码审查必然要取舍。本项目的取舍顺序是**固定**的，从上到下：

| # | 优先级 | 含义 | 违反的典型后果 |
|---|---|---|---|
| 1 | **数据不丢** | 任何一条已存在的记录都不能变得不可见或损坏 | 用户信任崩塌，且无法挽回 |
| 2 | **时间正确** | `created_at` 不被服务器时间覆盖；异常输入不产出假日期 | 记录被归档到错误的日期，历史被改写 |
| 3 | **离线正常** | 断网时读写仍可用，UI 不被网络阻塞 | 这是本 APP 的核心卖点，坏了等于没用 |
| 4 | **同步正确** | 重复提交幂等；Record 与 Mutation 同事务 | 数据重复或丢失 |
| 5 | **冲突正确** | 不静默覆盖用户内容；三方信息都保留 | 用户的编辑无声消失 |
| 6 | **基本交互** | 主路径可点、可输入、可撤销 | 用不了 |
| 7 | **UI 美观** | 符合 UI 设计规范 V2 | 不好用 |
| 8 | **动画** | 过渡自然 | 不够精致 |

**使用方式**：审查意见如果分属不同层级，**只看最高的那一层**。
「动画不够顺」和「同步会丢数据」同时出现时，后者是唯一的议题，前者可以完全忽略。

反过来，**高优先级没问题时，不要在低优先级上纠缠** —— 那会拖慢合并速度，
而速度本身是有价值的。

## 2. 什么必须人工审查

**机器能判断的交给机器（§3），机器判断不了的下面的清单。**

### 2.1 高风险区（改动这些地方，必须有人逐行看）

| 路径 | 为什么危险 |
|---|---|
| `src/db/db.ts`、`src/db/*Repository.ts` | IndexedDB schema 与迁移。改错 = 用户数据不可见 |
| `src/utils/time.ts`、`src/utils/timezone.ts` | 时间与时区。改错 = 历史归档日期被改写 |
| `src/sync/**` | 同步引擎、outbox、幂等、重试。改错 = 重复或丢失 |
| `src/domain/mutation.ts`、`src/domain/record.ts` | 数据模型与补丁合并语义 |
| `supabase/migrations/**` | 数据库迁移，**不可回滚** |
| `src/auth/**`、Supabase RLS 策略 | 越权 = 一个用户能看到另一个用户的数据 |
| `src/cloud/**` | 云端契约。改错 = 新旧客户端不兼容 |

### 2.2 存储键（**改名字时最容易踩的坑**）

下面三个字符串是**存储键，不是显示名**。改产品名时**绝对不能动**它们：

```ts
// src/db/db.ts
const DB_NAME = 'inspiration-todo'

// src/cloud/cloudConfig.ts
const STORAGE_KEY = 'inspiration-todo/cloud-config'

// src/cloud/supabaseClient.ts
storageKey: 'inspiration-todo/auth'
```

改动任何一个，浏览器都会认为这是一个**全新的空库**，用户的全部记录会「消失」
（数据其实还在磁盘上，但对 APP 不可见）。三处均已加警告注释。

产品名请改 `index.html` / `vite.config.ts` 的 manifest / `README.md`。

### 2.3 明确允许直接合并的改动

- 纯文档（`docs/**`、`README.md`、`LICENSE`）
- 纯注释、纯格式
- 依赖小版本升级且 `npm run verify` 通过
- 已由 CI 全绿覆盖的、无行为变更的重命名

## 3. 三级门禁

三级都必须通过。**上一级不过，下一级不用看。**

### 第 0 级 —— 编辑器 / 本地保存

TypeScript 语言服务 + oxlint 编辑器插件。
不需要配置，只要编辑器打开着就在生效。

### 第 1 级 —— 提交前（本地，秒级到十秒级）

由 `.githooks/` 提供，通过 `core.hooksPath` 启用（**零新依赖**）。

```bash
npm run setup     # clone 之后跑一次即可
```

| 钩子 | 检查内容 |
|---|---|
| `.githooks/pre-commit` | `npm run verify`（tsc + oxlint + vitest）。只改了文档时自动跳过 |
| `.githooks/commit-msg` | 提交信息符合 Conventional Commits（§6） |

**E2E 刻意不在这里跑**：它要起浏览器和 preview 服务，几十秒起步，
放在提交前会让人开始习惯性 `--no-verify`，那比没有钩子更糟。

### 第 2 级 —— CI（`.github/workflows/ci.yml`）

| Job | 内容 | 时机 |
|---|---|---|
| `verify` | `tsc -b` → `oxlint --deny-warnings` → `vitest run` | 每次 push / PR |
| `e2e` | `playwright install` → `npm run build` → `playwright test` | `verify` 通过后 |

`--deny-warnings` 的含义：**warning 也返回非零退出码**。
当前基线是 0 warning，这条门禁保证它不会悄悄涨回去。

### 第 3 级 —— 人工审查

见 §5 清单。

## 4. 测试放在哪一层

**默认策略：领域逻辑写单元测试，界面走 E2E，组件层默认不写单测。**

| 层 | 用什么 | 覆盖对象 |
|---|---|---|
| 领域 / 纯函数 | Vitest | `src/utils/`、`src/domain/`、`src/sync/`、`src/db/` |
| 界面 / 交互 | Playwright（`e2e/app.spec.ts`） | 全部组件、页面、导航 |
| 组件单测 | **仅限 E2E 触达不到的组件** | 目前只有 `ErrorBoundary` |

**为什么组件层默认不写单测**：本项目交互简单、组件多、状态基本来自
IndexedDB 的 live query。给每个组件写单测的维护成本远高于收益，
而 E2E 已经覆盖了真实主路径。**不为覆盖率数字写测试。**

**例外必须说明理由**。目前的唯一例外：

```
src/test/errorBoundary.test.tsx
理由：要触发错误边界，必须先让渲染期抛错 —— 生产构建里没有这个入口，
      也不该为了测试往生产代码里塞开关。这是 E2E 结构性触达不到的场景。
```

### 覆盖率

**本仓库不设覆盖率阈值。** 理由是：组件层不写单测，全局覆盖率会被 UI 代码
拉到一个没有意义的低值，然后大家开始为了数字写无价值的测试 —— 这是反效果。

**取而代之的是「新增逻辑必须带测试」的约定**：

- 改了 `src/utils/` / `src/domain/` / `src/sync/` / `src/db/` → **必须**补对应的
  `src/test/*.test.ts` 用例
- 修 bug → **必须**补一个能复现该 bug 的用例（否则它一定会回来）
- 改了交互 → 补一条 `e2e/app.spec.ts` 用例
- 纯 UI 样式调整 → 不需要

### 测试要测什么

按 §1 的优先级，测试的价值也是分层的：

| 值得写 | 不值得写 |
|---|---|
| 非法输入不产出假值（`NaN`、假日期） | 组件渲染出的 class 名 |
| 重复提交仍然幂等 | 内部函数的调用次数 |
| 断网后重新联网，数据仍完整 | 私有方法的实现细节 |
| 三方冲突时三份数据都保留 | 纯样式的快照 |
| 跨时区不会让归档日期漂移 | |

## 5. 审查清单

按 §1 的优先级从上往下逐条过。**上面的不过，下面的不用看。**

### 🔴 必须拦住（Blockers）

- [ ] **数据不丢**：没有任何已存在的记录会变得不可见；存储键（§2.2）未被改动，或已给出迁移方案
- [ ] **事务边界**：写入路径里 Record 与 Mutation 仍落在同一个 IndexedDB transaction
- [ ] **幂等**：重复提交同一个 mutation，服务端只生效一次
- [ ] **权限**：新增的云端读写路径有对应的 RLS 策略，且不依赖客户端过滤
- [ ] **迁移**：`supabase/migrations/` 的改动不可回滚，是否真的想清楚了
- [ ] **崩溃**：新增的渲染路径不会因为外部脏数据（云端返回的畸形字段）而抛错

### 🟡 应当修正（Suggestions）

- [ ] **时间**：`created_at` 不被服务器时间覆盖；时间函数对异常输入有明确行为
- [ ] **边界**：`split()` / `JSON.parse()` / 下标访问的结果都被校验过
- [ ] **测试**：按 §4 的约定补了对应层级的用例
- [ ] **错误处理**：`catch` 分支真的能兜住，而不是换个姿势再抛一次
      （这正是审计 §3.2 的教训）
- [ ] **N+1**：没有在渲染循环里发起 IndexedDB / 网络请求
- [ ] **重复**：没有把已经存在的工具函数再写一遍

### 💭 可以商量（Nits）

- [ ] 命名是否准确表达意图
- [ ] 注释是否解释「为什么」而不是「做了什么」
- [ ] 是否有更简单的实现
- [ ] 是否符合 UI 设计规范 V2 的形状/颜色语义

## 6. 提交与分支规范

### 提交信息（由 `.githooks/commit-msg` 强制）

```
<type>(<scope>): <描述>

[可选正文：为什么这么改]

[可选脚注：BREAKING CHANGE 等]
```

| type | 用于 |
|---|---|
| `feat` | 新功能 |
| `fix` | 修 bug |
| `refactor` | 重构，行为不变 |
| `perf` | 性能 |
| `test` | 测试 |
| `docs` | 文档 |
| `chore` | 杂项、依赖 |
| `build` | 构建配置 |
| `ci` | CI 配置 |
| `style` | 纯格式 |
| `revert` | 回滚 |

**scope 建议**：`db` / `sync` / `time` / `ui` / `auth` / `cloud` / `deps` / `docs`。

示例：

```
fix(time): 日期解析不再产出 "NaN月NaN日"

非法输入（空串、bad、2026-13-45）原先会渲染出假日期，
2026-13-45 甚至会被 JS 静默溢出成 2027-02-14。
现统一走 parseLocalDate() 校验，非法输入返回空串。
```

**正文写「为什么」，不写「做了什么」** —— 「做了什么」看 diff 就知道。

### 分支

单人项目直接在 `main` 上开发即可，但**每完成一个独立议题就提交一次**，
不要把三件事揉进一个 commit。理由：出问题时能单独回滚。

需要长时间试验时用 `feat/xxx` 分支，通过 PR 合回 `main`，
这样 CI 会在合并前跑一遍。

## 7. 例外：什么时候可以关掉一条规则

规则不是越多越好，但**关规则必须有记录**。

### 三种做法，按优先级

1. **改代码让它合规** —— 首选。绝大多数情况都能改。
2. **就地注释豁免** —— 当这条规则对本处代码**结构性不适用**时：

   ```ts
   // 空位格子没有身份可言 —— 位置就是它的身份，这里用 index 是刻意的。
   // oxlint-disable-next-line react/no-array-index-key
   if (!date) return <div key={`empty-${index}`} className="h-10" />
   ```

   **必须写清「为什么这里不适用」**，只写 `// eslint-disable` 的提交一律打回。

3. **全局关闭** —— 仅当这条规则对本技术栈**整体就是错的**：

   目前已全局关闭的 8 条及理由：

   | 规则 | 关闭理由 |
   |---|---|
   | `react/react-in-jsx-scope` | 本项目用新 JSX transform（`jsx: "react-jsx"`），不需要 `React` 在作用域内 |
   | `import/no-unassigned-import` | 会误报 `import './index.css'` |
   | `import/no-named-as-default` | `dexie` 的默认导出就是 `Dexie` 类，官方写法 |
   | `no-await-in-loop` | **同步逻辑必须顺序执行**，并行反而是 bug。这条规则在这里是反向的 |
   | `no-new` | `new Intl.DateTimeFormat(...)` 用于**校验时区合法性**，丢弃结果正是目的 |
   | `jsx-a11y/no-autofocus` | 本 APP 是「capture-first」，桌面端自动聚焦是刻意的产品决策 |
   | `promise/always-return` | 本项目统一用 `void promise.then(...)` 表达「故意不等待」，意图已显式 |
   | `unicorn/consistent-function-scoping` | 纯风格，无可观测收益 |

**注意最后一条：全局关闭必须是「规则错了」，不能是「改起来麻烦」。**

### `!` 非空断言的使用

允许，但**仅限长度由类型或字面量保证**的索引访问，且必须带注释：

```ts
// Uint8Array(16) 长度由字面量固定，索引 6 / 8 必然存在 ——
// 这里的 ! 表达的是「长度已由字面量保证」，不是「我猜它存在」。
bytes[6] = ((bytes[6]! & 0x0f) | 0x40)
```

`foo!.bar` 用在「我刚断言过它非空」的地方一律打回 —— 请改成 `foo?.bar`
或显式 `if (foo === undefined) ...`。

## 8. 流程

### 日常改动（单人，直接在 main）

```
1. 改代码
2. npm run verify            ← 或直接 git commit，钩子会自动跑
3. git commit -m "fix(time): ..."
4. git push                  ← CI 会自动跑三级门禁
5. CI 全绿 → 完成
```

### 需要审查的改动（高风险区 / 试验性改动）

```
1. 从 main 切分支：git switch -c feat/xxx
2. 改代码 + 补测试
3. npm run verify            ← 本地先过一遍
4. git push -u origin feat/xxx
5. gh pr create              ← 会自动带上审查模板
6. CI 全绿 + 按 §5 清单人工过一遍
7. 合并（squash 或 rebase，保持 main 线性）
```

### 审查者要做的

1. **先读 PR 描述**，确认「为什么」说得通。说不通就不用看代码了。
2. **先看测试**。测试改了没有？测试能不能复现描述里的问题？
   测试写得对，代码通常也差不到哪去。
3. **按 §5 清单从上往下过**，遇到 🔴 就停下来说清楚，不要继续往下翻。
4. **确认例外有理由**（§7）。
5. 给结论。

### 审查意见的写法

**必须具体到文件和行，必须解释为什么，必须是建议而不是命令。**

```
🔴 时间正确：非法输入会产出假日期
`src/utils/time.ts:97` —— `split('-')` 之后直接 `Number()`，没有校验。

为什么：实测 `formatMonthDay('')` 返回 `"NaN月NaN日"`；
`dayOfWeek('2026-13-45')` 静默返回 0（JS 把日期溢出到 2027-02-14），
不报错但日期是错的 —— 这比直接失败难排查得多。

建议：
- 抽出 `parseLocalDate()` 做唯一校验入口，非法输入返回 `null`
- 各格式化函数改为返回 `''`，绝不返回 `NaN`
- 补一个覆盖空串 / 非法月份 / 非法日期的用例

参考：docs/代码审查-基线审计报告.md §3.1
```

**标记约定**：

| 标记 | 含义 | 处理 |
|---|---|---|
| 🔴 | Blocker | 必须改，否则不合并 |
| 🟡 | Suggestion | 应当改，可以另开一次提交 |
| 💭 | Nit | 可以商量，也可以不改 |
| ✅ | 值得表扬 | 说出来 —— 明确什么是好代码，比只说哪里错更有效 |

**遇到不确定的，问，不要猜**：

> 这里把 `pending` 和 `failed` 一起取出来排序，是有意为之吗？
> 我看 `reconcile` 只处理 `pending`，如果 `failed` 混进来会不会被误判成待发送？

## 9. 机制自身的演进

**这套机制是「棘轮」，只往紧的方向转。**

- 基线是 0 warning / 0 error。**任何新增的 warning 都视为回归。**
- 想加一条新规则时，先看开启后的实际报错数（`npx oxlint -c <临时配置>`），
  评估改动面后再决定 —— 本项目已经用这个方法评估过 4 个 TS 开关和 3 个 lint 分类。
- 想放宽某条规则时，**必须在本文档 §7 记录理由**，否则视为降低标准。
- 每次审计（建议每个大版本一次）都把新的实测结论补进基线审计报告，
  而不是覆盖旧结论 —— 保留历史才能看出趋势。

### 已知的下一步（不急于做）

| 事项 | 触发条件 |
|---|---|
| 引入 `@vitest/coverage-v8` | 当领域层代码量翻倍，或出现「改 A 坏了 B」时 |
| 清理 15 个死导出 | 专门做一次清理时（见审计报告 §5.2） |
| 启用 `noPropertyAccessFromIndexSignature` | 当 `import.meta.env` 的访问点收敛到少数几处时 |
| 拆 `recordRepository.ts` / `ConflictService.ts` | 当它们超过 500 行，或职责开始交叉时 |

## 附：评审者速查表

```
先问三件事：
  1. 数据会不会丢？        → 存储键 / 事务 / 迁移
  2. 时间会不会错？        → created_at / 时区 / 异常输入
  3. 断网还能用吗？        → 是否被网络阻塞

再看三件事：
  4. 重复提交还幂等吗？
  5. 冲突时会静默覆盖吗？
  6. 测试补了吗、补对层了吗？

最后才看：
  7. 好看吗？  8. 动画顺吗？
```

**记住**：审查的目的是让代码变好**并且**让写代码的人变强。
指出问题的同时说清楚「为什么」和「怎么改」—— 一份只说「这里不对」的审查，
等于把问题原样扔回去，没有产生任何价值。
